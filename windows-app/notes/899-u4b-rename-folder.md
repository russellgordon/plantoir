## For documentation 12

- **An edit inside a moved folder (or of a moved file), U4b** (W8; `opKinds.wholeOps`' one exception): an op naming a path at or inside a `move`'s `to`, after the move in the step, is carried by it. Forward (make and Redo) the edit is judged where the file is BEFORE the move (`from` + the rest of the path), the move goes in first, and the edit is staged only at its turn, once its folder is there (staging first would make the folder at `to` and the move would be refused). Backward (Undo) the edit is taken back first, then the move, which the plan judges with each carried file as the edit's other side; the swap judges the move's pair without its own staged files and kept `-orig` files inside the folder, and renames those it holds when the folder moves (and when a reversal moves it back), so the tidy finds them. Anything naming a path inside a move's `from` is still unreadable, a barrier.
- **A folder move's listingSha is not a blob** (W8): the mac's `UndoOp.namedBlobs` asked for it, so `JournaledWrite.vet` refused every folder move as notReadable until U4b. Check that Windows' vetting does not do the same.

- **The outgoing bytes of an Undo or a Redo** (W4c): under the lock and before the swap, every page a whole-file op moves FROM THE LIST, whose outgoing bytes the other direction needs and the list lacks, has them written into the list; when the list will not take them they are kept beside the page under the swap's own `-undo-orig` / `-redo-orig` name, unless a kept copy there already holds them. The `U4a, LOW 4 (a)` row pins the kept branch. A door that skips this deletes the only copy at the swap's tidy (the Redo then comes to contentMissing).
- **Kept copies thinned** (W4c): after each move, the step's kept copies beside a page are thinned to one per SHA-256, the newest move's copy kept; an unreadable copy is never removed. `U4a, LOW 4 (b)` (seven moves, two files) pins it.
- **The trail line `undo kept what it replaced`** says a page was put back "from what was kept beside it" ONLY when it was, decided PAGE BY PAGE (U4b part one's review, LOW 1): the mac's `UndoTrail.keptWhatItReplacedLine(…putBackFromAKeptOriginal:)` takes the names of the pages the check's uses name; a page the list gave says "Undo put back “A.md”, but the list could not keep a copy …", and a step with pages both ways says "Undo put back “A.md”, and put back “B.md” from what was kept beside it, but …" (`activityTrail.mustRecord` → `carries`). W4c copies it.
- **Recovery of a step killed between a move and the edits it carries** (W8): read a carried edit where its folder is now (under the move's `from` while nothing is at `to`), judge the carrying move as if the step's edits inside were taken back and without the step's own staged and kept files inside the folder, and tidy (and judge the kept copies) beside the carried page at the folder's old place too, so nothing is left inside the folder moved back. `UndoRecovery.fileStates`, `carryingMoveState`, `placesStagedBeside` on the mac.
- **A capitalisation-only rename** (W8): see `opKinds.move`; one item under two spellings is judged by the spelling the folder lists, and the rename goes in only while the folder lists the spelling it leaves.

- **A `course_config.json` that is a link** (W8): the mac plans the Save where the link leads (`CourseConfiguration.fileALinkLeadsTo`, following each link of the last component, as many as the system follows) and leaves the link a link. Measured before the fix on the mac: `Data.write(.atomic)` to a link REPLACES the link with a plain file (the pre-U4a Save did that); U4a's door refused it as changed since and the Save could not be made with the switch off. Windows' Save should write through a reparse point the same way.
- **After a Save's make** (W8): the app's copy is the file read back, so another program's change of another member between the plan and the make is in memory too (U4a review 1, LOW 2).
- **Save's last try** (W8; U4a review 1, LOW 3, meant for the U4a note, which was folded in before this landed): a step refused because one of its own members changed between plan and make is planned again up to three times, four tries in all; the fourth refusal writes nothing, keeps the edits unsaved in the sheet, and the sheet says "Could not save: The file “course_config.json” couldn’t be saved." (the mac's `CocoaError(.fileWriteUnknown)` sentence), pinned by `UndoCourseSettingsStepTests.testAFourthRefusalInARowWritesNothingAndKeepsTheEditsUnsaved`.

- **Rename folder as one step** (W8): plan the walk off the UI thread without writing; each relinked page's `before` is the walk's own read; a page at or inside a moved folder is read under the move's `from` and named under its `to`, spelled as the rename spells it (a case-only rename must not be named by the spelling the disk lists). Every writer of `course_config.json` uses member edits (`editJSON`); a whole-file write below a Save's member edits is refused by the Save's Undo by design.
