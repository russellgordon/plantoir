Use the project's `FolderIdentity.canonicalPath`, not `resolvingSymlinksInPath()`, which strips `/private` (CLAUDE.md, "How the toolchain ships"). ## Next piece: a place inside the folder is found whatever its spelling (2026-11-26)

The fix is committed as 02191b6a9.

- **The rule lives in one function, `RestoreSwap.placeInside(_:of:)`.** It compares the text first. If that fails, it compares each folder ABOVE the place, in the disk's own spelling (`FolderIdentity.canonicalPath`), against the folder's spelling, and keeps the names below the match exactly as written. The place itself is never resolved, so a link inside a course keeps its own place and is never followed.
  - `RestoreSwap.relative(_:to:)` calls it, and so does `CourseRestorer.relativePath(of:under:)`, the one-section restore's walk, which had the same text comparison.
  - No existing function states this rule. `FolderIdentity.canonicalPath` resolves a whole path, including the place. `UndoFolderPlaces.relativePath` (JournaledStep.swift) also resolves the place, so a link inside a course came out outside the course (shown by must-fail 2). `resolvingSymlinksInPath()` strips `/private`. `placeInside` therefore uses `FolderIdentity.canonicalPath` for the folders above the place only.
- **Left as they are:** the comparisons in `RestoreSettle` (`found.url` against `mine`, and `claimed` against `staging` and `original`). They compare two URLs built from the same staging folder, and when the two are spelled differently, the worst outcome is a `rename` of a path onto itself, which does nothing.
- **Tests, in `CourseRestorerStagedTests`:**
  - `testAPlaceSpelledThroughTheLinkAboveTheFolderIsStillInside`
  - `testAWalkThroughALinkedWorkingFolderKeepsEachFileAndALinkInsideStaysALink`
  - Both use a working folder reached through a link made on purpose (`LinkedWorkingFolder`, built under the disk's own spelling of the temporary folder), so the temporary folder's `/var` spelling plays no part.
- **Must-fail** (each sabotage built and run, then removed, `git diff` clean):
  1. The old text-only comparison put back: both new tests red (8 failures).
  2. The place itself resolved (`UndoFolderPlaces.relativePath`): the link test red, 4 failures ("the link is kept at its own place", "as a link").
- **Runs:**
  - All four classes passed in the final run: `CourseRestorerStagedTests`, `RestoreRecoveryTests`, `RestoreWholeCourseContractTests` and `WholeCourseRestoreDoorTests`.
  - `UndoWriterScanTests` and the nine other classes passed too.
- **Still red at times, for another reason (not fixed):** `CourseRestorerStagedTests` failed in 4 of its 5 runs today, each time in one to three of these tests:
  - `testFilesThatArriveWithOldDatesAfterTheArchiveAreKept`
  - `testNamesBackupsLeaveOutDeeperThanTheTopAreKept`
  - `testAHiddenFileChangedAfterTheArchiveIsKept`
  - `testAddOnsLeftOutOfTheArchiveOnPurposeAreNotKept`
  - `testALockedPageInsideStillRestoresAndLeavesNothingStaged`

  The cause, measured with a temporary print in `heldByTheArchive` (since removed):
  - The archive's start reaches the check rounded DOWN to the millisecond (in a failing case 1795690548.277).
  - The fixture writes its pages a fraction of a millisecond before it takes that start (`changed` 1795690548.2771568).
  - So `changed >= archiveBegan` holds, and a page the archive does hold is judged written after it and kept in a "not in the archive" folder.

  This is a false keep, in the safe direction: nothing is lost. The fixture writes and archives within the same millisecond, which a teacher's restore never does. The fix belongs to the next piece's owner: either a fixture that waits for the clock to pass a millisecond, which must not be a timed sleep, or an engine that compares against the start rounded UP.
