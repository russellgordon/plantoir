1. **A relink that does not move (one place for `from` and `to`) does not work through the door as relink-1 to -3 left it; not built here.** Russell's ruling of 2026-11-26 (the in-between link is re-pointed where it stands) needs it. Found by reading the door, at three places:

   - Judged: `UndoCheck.wholeState` reads `from` by `linkShaBefore` and `to` by `linkShaAfter` at ONE place; a link holding the old text reads holds-the-content at `from` and holds-something-else at `to`, so it is `.neither` both ways (never `.before` or `.after`).

   - Recovery: `removeTheLinksJustMade` treats "both texts standing" as two places; with one place both can never stand.
   The smallest next piece (door, about relink-1's size): a `move` with `from == to` byte for byte and the pair `linkShaBefore`/`linkShaAfter` is readable (one more exception beside the capitalisation-only move; not for `moveApart`/`setAside`); judged at the one place: old text `.before`, new text `.after`, anything else `.neither`, unreadable `.cannotTell`; swapped as make the new link under the staged `-new` name beside the place, then `rename` it OVER the old link (one atomic `rename`, never `RENAME_EXCL`, only after re-reading the old link holding the source's text, `RENAME_SWAP` or a check-then-rename; the window between re-read and rename is the same as every file swap's), reversal the same with the texts exchanged; recovery: a staged `-new` link is tidied as today (`relinkStaged`), and there is no both-standing moment, so `relinkRenamedIn` does not arise; a contract sentence in `opKinds.move`, `checkCases` and `recoveryCases` rows and the Python model.
