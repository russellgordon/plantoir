## The advisory

GHSA-fc5q-39xc-vjpf (CVE-2026-112366), high (CVSS 3.1 7.5, AV:N/AC:L/PR:N/UI:N/A:H),
published 2026-10-19: "Picomatch through 4.0.7 contains a regular expression
denial of service vulnerability that allows attackers to block the event loop
by supplying single-branch repeated extglob patterns. Attackers can provide
globs like `+(*)` or `+(*a)`, which `analyzeRepeatedExtglob` in
`lib/parse.js` skips, causing exponential backtracking against short crafted
strings." Vulnerable range `<= 4.0.7`; **first patched version: none.**
4.0.7 (2026-08-24) is the newest picomatch on npm that day, so every
published picomatch is affected.

npm's own entry says `"fixAvailable": true` for picomatch. That is the older
two advisories' fix (2.3.2, range `<2.3.2`), not this one's.

## Which trees, which versions, brought in by what

Only **quartz**. The other four trees report no advisory at all, so none of
them carries an affected picomatch.

In Quartz v4.5.0's lockfile there is exactly one picomatch,
`node_modules/picomatch` **2.3.1**, and exactly one package that depends on
it:

    quartz 4.5.0 (root) -> globby ^14.1.0 (14.1.0)
      -> fast-glob ^3.3.3 (3.3.3)
        -> micromatch ^4.0.8 (4.0.8)
          -> picomatch ^2.3.1 (2.3.1)

No dev-only path, no second copy. chokidar 4.0.3 (Quartz's and Sass's) and
readdirp 4.0.2 do not use picomatch; there is no anymatch in the tree.

## Why no version was taken

There is nothing to take: no published picomatch is outside the vulnerable
range. Even once a fix ships, micromatch 4.0.8 allows only `^2.3.1`, so a fix
in 4.x alone would not fit the range its dependent allows; it would need a
2.x release, or micromatch/fast-glob moved, which is Quartz's own lockfile.
Moving that waits for Quartz 5 (#512), the standing position of
2026-10-24. Taking 2.3.2 inside the range (which would clear the two older
picomatch advisories) is the same lockfile move and does not clear this one.

## How a pattern could reach picomatch

The advisory needs the attacker to supply the PATTERN. The text matched
against it (file names, paths) is not what backtracks into the exponential
case unless the pattern is a single-branch repeated extglob. So the question
is where every pattern picomatch compiles comes from, while a teacher builds
or previews.

picomatch is reached only through micromatch, which only fast-glob uses, which
only globby uses. Every globby call in the image:

- `quartz/util/glob.ts` → `globby(pattern, { cwd, ignore: ignorePatterns, gitignore: true })`, called with
  - `"**/*.*"` from `build.ts` (Plantoir's `patches/build.ts`, the same call),
  - `"**"` from the Assets and Static emitters, and from Plantoir's
    `support/quartz/plugins/emitters/plantoirAssets.ts`,
  - ignore `"**/*.md"` (Assets, plantoirAssets) plus
    `cfg.configuration.ignorePatterns`, which is Quartz's own
    `["private", "templates", ".obsidian"]` in `quartz.config.ts`.
    `build_site.py` edits that file only for locale, baseUrl, analytics and
    the social-preview emitter; nothing in Plantoir's build or apps writes
    `ignorePatterns` (scripts/geogebra.py only describes it, and
    one check script sets its own copy of the same three).
- `quartz/cli/handlers.js` → `globby(["**/*.ts", "quartz/cli/*.js", "quartz/static/**/*", "**/*.tsx", "**/*.scss", "package.json"])`, its own watcher list, under `--watch`.
- globby itself adds `**/.gitignore` (to find ignore files) and its default
  ignores `**/node_modules`, `**/flow-typed`, `**/coverage`, `**/.git`
  (`ignore.js`), and `directoryToGlob` turns a directory entry into
  `dir/**`.

None of them holds an extglob. The two places something from the course folder
could look like a pattern, checked:

- **A `.gitignore` inside the course folder.** `gitignore: true` reads it,
  but globby 14.1.0 hands its lines to the `ignore` package
  (`gitIgnore().add(patterns)` in `ignore.js`), which has its own matcher;
  they never reach fast-glob or picomatch. The same is true of `isGitIgnored()`
  in `build.ts`'s watcher.
- **File and folder names.** fast-glob reads them from the disk and matches
  them against the patterns above; `cwd` is a path, not a pattern. A name such
  as `+(*)` is matched as text, never compiled.

During a preview, a visitor's request is served by serve-handler, which
matches its own configuration with minimatch (accepted separately), and the
live-reload websocket is ws; neither reaches picomatch. Nothing a student's
browser does reaches it, and a built site carries none of it.

**Exposure:** the teacher's build only, which is the existing picomatch
entry's. The patterns picomatch compiles are all written into Quartz's and
Plantoir's code, and nothing a page, a file name, a `.gitignore` or a preview
visitor supplies is ever compiled as one.
