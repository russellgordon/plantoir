## What is still red, and why (not the merge's doing)

- The merge did not cause it. I checked out the pre-merge head ebd1ffbd4, built it and ran `CourseRestorerStagedTests` and `RestoreRecoveryTests`: they fail in exactly the same tests with the same counts (31 and 7). I did not run the other two classes on ebd1ffbd4, but their failures have the same signature.
- The cause, measured with a short script on this Mac: when `FileManager.enumerator(at:)` walks a folder under `FileManager.default.temporaryDirectory` (`/var/folders/…`), it returns entries as `/private/var/folders/…`.
- `RestoreSwap.relative(_:to:)` compares path strings, so it does not strip the prefix. `keepWhatTheArchiveMayNotHold` and the settle then work with whole paths in place of relative ones.
- The effects: a lookup in the listing misses (so files are kept that should not be), a move's source does not exist (so `everythingMoved` is false and staging is left), and the kept folders come out empty.
- A teacher's working folder reached through a symbolic link would meet the same fault, so this is a real engine bug and not only a quirk of the tests.
- Not fixed here: the brief allows fixes only for what the merge broke. The likely fix is to compare paths in one canonical form on both sides of `relative`. Use the project's `FolderIdentity.canonicalPath`, not `resolvingSymlinksInPath()`, which strips `/private` (CLAUDE.md, "How the toolchain ships"). Then check every other walk in `RestoreSwap` and `RestoreSettle` that uses `relative`. and to check every other walk in `RestoreSwap` and `RestoreSettle` that uses it.
