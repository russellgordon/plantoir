# macOS native routing measurements, TEN trials, 2026-08-15
# Apple M4 Pro (48 GB), macOS 26.6, llama.cpp b10435, Metal, native.
# llama-server --ctx-size 16384 --threads 6 --n-gpu-layers 999 --jinja --parallel 1
# Suite: research/ai-assist/trimmed-surface-suite.py, SHIPPED configuration
#        (--date-appended --real-course), 29 probes x 10 trials = 290 responses.
# Tool surface: the SAME tools-local.json the 3-trial run used (15 tools,
#        13,858 bytes, 3,417 prompt tokens as Qwen2.5 tokenises it). Byte-for-
#        byte identical across every model below, so the comparison is fair.
# "Tomorrow" is 2026-08-16 in every run, exactly as in the 3-trial file.
#
# WHY THIS RUN EXISTS
# -------------------
# macos-native-results.txt vetoed Qwen2.5-3B on 2 polarity inversions out of 3
# trials, and no other family had been tried in the 2-4B band. Two questions:
#   (1) does the 3B veto survive 10 trials, or was 2/3 noise?
#   (2) is the failure Qwen2.5-3B-specific, or a property of that size?
# Both are now answered, and the answer to (2) changes the ladder.
#
# A NOTE ON WHAT 10 TRIALS BUYS
# -----------------------------
# The suite runs at temperature 0.1, so repeated trials of one probe are very
# nearly deterministic — most probes below are 10x the same tool. Ten trials
# therefore does NOT give a precise failure RATE; what it gives is the
# distinction between "this model systematically does the wrong thing on this
# phrasing" and "it wobbled once". That is exactly the distinction the veto
# needed, and the 3B's 2-of-3 turns out to be the systematic kind.
#
# HEADLINE
# --------
#                              all 290      Windows' 180   INVERSIONS  malformed  resident  warm turn  download
#   Qwen2.5-1.5B  (shipped <16GB)  203 (70%)   143 (79%)         0          0      1.75 GB   0.35 s    1.12 GB
#   Qwen2.5-3B    (vetoed)         219 (76%)   129 (72%)         9          0      2.84 GB   0.60 s    2.10 GB
#   Qwen2.5-7B    (shipped >=16GB) 270 (93%)   170 (94%)         0          0      5.72 GB   1.14 s    4.68 GB

#   Phi-4-mini (3.8B)               20 ( 7%)    20 (11%)         -          -      4.73 GB   0.43 s    2.49 GB   NO TOOL CALLING

#   Qwen3-4B      (--reasoning off) 280 (97%)  180 (100%)        0          0      5.04 GB   0.74 s    2.50 GB

#
#   "Windows' 180" is the 18 non-promise-card probes x 10 — the like-for-like
#   column against the Windows 94%. INVERSIONS counts every polarity probe
#   answered with the opposite verb, not only the ones the suite's own counter
#   catches (its test is `probe.startswith("hide")`, which misses "card:
#   unpublish by name" and "no course named: hide"); every inversion found
#   below was a real WRITE tool, not a plan_ tool.
#
# ANSWER 1: THE 3B VETO HOLDS, AND IT IS WORSE THAN 3 TRIALS SUGGESTED
# --------------------------------------------------------------------
#   Qwen2.5-3B inverted 9 times out of 10 on "HIDE - the inversion case",
#   calling publish_pages on a page the teacher asked to hide. The 3-trial
#   run's 2/3 was not noise and not bad luck — it is what this model does with
#   that sentence. It also answered "card: unpublish by name" with
#   undo_last_change 10/10 and "hide, informal" with undo_last_change 10/10.
#   Keeping it out of the ladder was correct.
#
# ANSWER 2: IT IS NOT QWEN-SPECIFIC, BUT IT IS NOT THE SIZE EITHER
# ----------------------------------------------------------------
#   Llama-3.2-3B, a different family at the same size, inverted 10 times out of
#   10 on the same probe — 9x publish_class_on, 1x publish_pages. Two families,
#   both ~3B, both publish a page they were asked to hide. That looks like the
#   size until you run Qwen3-4B, which is 0/290 inversions and 100% on the
#   Windows probe set. So it is not "2-4B is unsafe"; it is that the 2024-era
#   3B models are unsafe on this surface, and a 2025-era 4B is not.
#
#   Llama-3.2-3B is disqualified twice over: besides the inversions it typed
#   `"section": "1"` as a STRING on essentially every call (305 type coercions
#   across 290 responses) and returned 7 malformed responses the server could
#   not parse into a tool call at all.
#
# TWO MODELS COULD NOT DO TOOL CALLS AT ALL — reported, not dropped
# -----------------------------------------------------------------
#   Phi-4-mini-instruct and Gemma-2-2b-it both scored 20/290. That 20 is
#   "deletion - no such tool" and "out of scope", the two probes where
#   declining is the right answer; they declined all 290 because they never
#   emitted a tool call at all. Diagnosed directly rather than guessed:
#
#     Gemma-2-2b-it   — /props chat_template is 591 chars and contains no
#                       reference to `tools` or `tool_calls`. llama.cpp b10435
#                       did NOT polyfill a generic tool format: it silently
#                       dropped the tools array. The prompt the server actually
#                       read was 34 tokens instead of ~3,417. `tool_choice:
#                       "required"` changed nothing — no error, no tool call,
#                       just prose asking what platform we are on.
#
#     Phi-4-mini      — /props chat_template is 423 chars and does mention
#                       `tools`, but only as `message['tools']` on a SYSTEM
#                       message. Confirmed against microsoft/Phi-4-mini-instruct
#                       tokenizer_config.json on the Hub: the official template
#                       is byte-identical to the one in the GGUF, and it has no
#                       branch for the OpenAI-style top-level `tools` array. So
#                       an OpenAI-shaped request renders 30 prompt tokens and no
#                       tools. Also unaffected by tool_choice: "required".
#
#   Neither is a quantisation or a repo problem, and neither can be fixed by
#   swapping GGUFs — the templates are what they are. A model that cannot take
#   an OpenAI tools array is disqualified for this job whatever it benchmarks.
#
# QWEN3-4B: THE THINKING TOKENS ARE THE WHOLE STORY
# --------------------------------------------------
#   As shipped (thinking on) Qwen3-4B scores 39% and takes a 4.14 s warm turn.
#   That is not a routing failure: it is the 256-token max_tokens budget being
#   eaten by the <think> block, so 196 of 290 turns ended with no tool call at
#   all. Latency went from sub-second to 4 s for the same reason.
#
#   With `--reasoning off` (llama-server b10435; the per-request equivalent is
#   chat_template_kwargs {"enable_thinking": false}) the same weights score
#   280/290 and 180/180 — a PERFECT score on the Windows-comparable set, better
#   than the 7B, with zero inversions, zero malformed calls, zero type
#   coercions, zero fabricated dates, and a 0.74 s warm turn. Its only misses
#   are the same read-only "card: plan a publish" -> plan_publish_class_on that
#   the 7B also gets wrong 10/10; nothing is at stake there beyond the shape of
#   the answer.
#
#   Qwen3-1.7B behaves the same way (26% thinking, 84% not) but is not safe to
#   recommend: with reasoning off it filled in date=2026-08-15 — TODAY — on 20
#   of its 40 "tomorrow" calls, i.e. it would publish today's class when asked
#   for tomorrow's. No inversions, but the wrong day is still the wrong page in
#   front of students.
#
# RESIDENT MEMORY IS MOSTLY KV CACHE, AND THAT IS ADJUSTABLE
# -----------------------------------------------------------
#   Qwen3-4B's 5.04 GB resident at --ctx-size 16384 is 2.5 GB of weights plus
#   ~2.4 GB of KV cache (36 layers x 8 KV heads x 128, fp16). Shrinking the
#   context leaves the routing bit-for-bit identical and gives the memory back:
#
#       ctx 16384   5.04 GB   280/290   180/180   0 inversions   0.74 s
#       ctx  8192   3.87 GB   280/290   180/180   0 inversions   0.74 s
#       ctx  4096   3.22 GB   280/290   180/180   0 inversions   0.74 s
#
#   All three were measured, not extrapolated. 8192 is the one to ship: the
#   tool surface alone is ~3.4k tokens, so ctx 4096 leaves under 700 tokens for
#   the conversation and will start truncating on a multi-turn chat, while 8192
#   leaves ~4.7k. The 1.2 GB saved between 16384 and 8192 is the difference
#   between "fits on an 8 GB Mac" and "does not".
#
# RECOMMENDATION
# --------------
#   8 GB Mac    Qwen3-4B Q4_K_M with reasoning OFF at --ctx-size 8192.
#               3.87 GB resident, 2.50 GB download, 0.74 s warm turn, and it
#               routes at 100% on the Windows-comparable set with zero
#               inversions. This replaces the 1.5B's 79% — a 21-point gain on
#               the machines that currently get the worst model. It costs
#               2.1 GB more resident than the 1.5B, and that is the one thing
#               left to weigh: 3.87 GB on an 8 GB Mac that is also running
#               Colima and the Quartz container is tight, and it should be
#               tried on a real 8 GB machine with the container up before it
#               ships. ctx 4096 buys back another 0.65 GB (3.22 GB) at the same
#               100%, but leaves under 700 tokens of room after the tool
#               surface, so treat it as the squeeze, not the default. Only if
#               BOTH are too tight does Qwen2.5-1.5B (1.75 GB, 79%) stay.
#
#   16 GB Mac   Qwen3-4B Q4_K_M with reasoning OFF at --ctx-size 16384.
#               It beats the 7B on accuracy (97% vs 93% overall, 100% vs 94%
#               on the Windows set), matches it on safety (zero inversions
#               both), and is faster and smaller on every axis: 5.04 GB vs
#               5.72 GB resident, 0.74 s vs 1.14 s warm turn, 5.85 s vs 9.18 s
#               cold read, 2.50 GB vs 4.68 GB to download. There is no measured
#               reason left to ship the 7B. Note the one thing the 7B does that
#               the 4B does not: nothing, on this suite.
#
#   Both tiers   REASONING MUST BE OFF. Shipping Qwen3 with thinking enabled
#               and a 256-token budget turns a 97% router into a 39% one. If
#               the app cannot pass --reasoning off, it must send
#               chat_template_kwargs {"enable_thinking": false} per request,
#               and that needs a test that fails loudly if it stops working.
#
#   Qwen2.5-3B  stays vetoed. 9/10 inversions.
#   Llama-3.2-3B vetoed: 10/10 inversions, plus string-typed section numbers.
#   Phi-4-mini, Gemma-2-2b-it: disqualified, cannot tool-call.
#
# WHAT SURPRISED ME
# -----------------
#   1. Two different families invert on the SAME sentence. 'Hide tomorrow's
#      class again ... the page is "Ohm's Law"' is the one probe that breaks
#      3B-class models, and it breaks them toward publishing. The words
#      "tomorrow's class" appear to out-pull the word "hide": Llama-3.2-3B
#      answered it with publish_class_on, the by-DATE publisher, 9 times out
#      of 10. That phrasing deserves a permanent regression test of its own.
#   2. A 4B model beating a 7B on the metric that matters, while being smaller,
#      faster and safer.
#   3. That the failure mode of a "better" model can be a config default. The
#      difference between 39% and 97% on identical weights is one flag.
#
# Full 290-row probe tables for every run are in the scratchpad at
# routing-run/<label>.txt; the condensed per-probe tables follow.
