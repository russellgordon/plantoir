WHAT THE max_tokens CAP DID TO ROUTING (ISSUE #166)
===================================================

THE FIRST THING TO KNOW: THIS SUITE CANNOT SEE THE FIX
------------------------------------------------------
Issue #166 is two changes, and only one of them is measurable here.

  1. The app now sends `"max_tokens": 512` (`AssistModelClient.mostTokensPerReply`)
     where it sent nothing before.
  2. The app now REFUSES to run a call parsed out of an answer the server
     ended on `length` rather than on the model finishing.

`trimmed-surface-suite.py` scores the tool NAME the model chose. It does not
run the app, so it cannot see (2) at all — nothing here is evidence that the
refusal works, and `AssistCutOffAnswerTests` in the mac suite is where that
lives. What this file answers is the ONE question a cap raises and a unit test
cannot: **does bounding the reply change which tool the model picks?**

The visible effect of (1) in these runs is confined to the length/TRUNCATED
lines. Everything else is expected to be — and is — identical.

**And it cannot show a "win" either.** A cap can only be neutral or harmful to
routing. The gain it buys is a teacher not waiting 41 to 95 seconds for an
answer that was never going to be usable, and that gain is a clock, which this
file reports and deliberately does not score.

AN EQUIVALENCE TO CARRY FORWARD
-------------------------------
**`metal-routing-results.txt`'s `H` arm — and every `--app-body` number in this
folder taken before 2026-09-19 — is `--app-body --uncapped` today.** The flag
was added by #166 so the old body stays reproducible. A run made with plain
`--app-body` after 2026-09-19 is measuring a DIFFERENT request, and comparing
it with an older `--app-body` figure is not like-for-like.

WHAT THIS NUMBER IS NOT
-----------------------
  - **Not a pass rate.** Temperature 0, near-greedy: ten trials of a probe are
    usually ten copies of one answer. Ten trials distinguishes "this model
    systematically does this" from "it wobbled once".
  - **Not what a teacher experiences.** Five of the 29 probes never reach the
    model in the app (`AssistCardCommand` answers them in code), and the app
    settles the course, the section and relative dates before any call runs.
  - **Not a gate.** Nothing in either test suite checks routing, deliberately.
  - **Not a comparison across days.** `--date-appended` puts the date in every
    probe, so BEFORE and AFTER were run on the SAME day on purpose.

Three things are worth saying about those numbers rather than leaving them to
be inferred.

  * **The token count is exact and repeatable in both directions.** 5,435 in
    all twenty uncapped trials across two runs eight hours apart; 512 in all
    ten capped trials. The cap is spent to the token.
  * **The engine's own accounting agrees about WHAT stopped it.** In the
    uncapped server logs the slot reports `stop processing: n_tokens = 8191,
    truncated = 1` ten times - 2,756 prompt + 5,435 written = 8,191, the
    context. In the capped log `truncated = 1` appears **zero** times and the
    largest `n_tokens` is 3,268. The stop moved from the context to the cap.
  * **The clock is not a clean 41 -> 4 s, and it would have been dishonest to
    round it there.** The afternoon machine was busier than the morning one
    (another measurement's llama-server was resident for most of the run), so
    the uncapped runaway got WORSE - up to 94.6 s - while the capped one cost
    6.0 to 6.3 s. The like-for-like pair is CONTROL against CAPPED on the same
    afternoon: **48.7-94.6 s becomes 6.0-6.3 s**. The engine's own rate for
    those generations says why the afternoon is slower rather than different:
    132.9-133.8 tok/s in the morning, 57.5-111.8 tok/s (median ~70) in the
    afternoon's uncapped arm, 82.0-85.4 tok/s in the capped one. A teacher on
    an idle machine would see roughly 4 s; nobody measured an idle machine
    today, and this file does not claim one.

THE SHAPE THE HEADROOM ARGUMENT DID NOT COVER: list_pages PATHS
---------------------------------------------------------------
The 512 was justified against the shape a TEACHER names - page titles typed
into the sentence. One shape was left unmeasured and said so in three places:
the two-lap one, where the model calls `list_pages`, the runner hands back up
to `AssistToolRunner.mostPagesListed` (**60**) entries as relative PATHS
(`AssistSectionGraph.relativePath`), and the next turn may echo them into a
`publish_pages` call. Measured now, at the request of the #166 plan review.

**Source of the paths.** A REAL course on this Mac, read-only: `ICS3U` section
1 in the working folder `~/Desktop/Class Websites`, 257 markdown pages.
`ClassPages.pagesOfSection` was reproduced exactly - the same skips
(`.merged_output`, `node_modules`, `.internal`, other sections), the same
lowercased-path sort - so the sixty are the sixty `list_pages` would really
hand back. The course code was rewritten to VVH2O so the arms and this
measurement name the same course; the codes are the same length. An example:

    courses/VVH2O/College Board Curriculum/1. Computational Solution Design.md

**A. Tokenized against the model's own tokenizer** (llama-server `/tokenize`,
the tool-call text a Qwen chat template emits). The `.small` and `.large`
weights gave the SAME counts on every row - Qwen2.5 and Qwen3 share a
tokenizer - so one column serves both:

    paths    tokens    (the first 60, as list_pages hands them back)
      1         50
      5        110
     10        194
     20        349
     30        497
     31        516   <-- the crossing: 30 still fit, 31 do not
     40        654
     50        805
     60        975

    paths    tokens    (the 60 LONGEST paths in the same section: the worst
      20       412      case inside one section)
      25       498
      26       516   <-- the crossing: 25 still fit, 26 do not
      40       800
      60      1231

**So 60 paths do NOT fit inside 512: they are 975 tokens, and the call crosses
the cap at 31 of them (26 for the longest-path worst case).** The caveat stays,
and it is now a risk with a number rather than an unknown.

**B. One generation of the shape, to see whether the model actually does it.**
A conversation primed the way `AssistAgent` primes one - the shipped system
prompt, "Publish everything in Unit 3 for VVH2O section 1", the assistant's
`list_pages` call, and a `role: "tool"` message carrying exactly what
`AssistToolRunner.listPages` puts in `outcome.detail` (the 60 paths, one per
line, plus its "...and 197 more" tail) - then "Publish all of those." with the
app's own body, cap included. `.small`, three trials:

    prompt_tokens       3766
    completion_tokens     35        (three trials of three, identical)
    finish_reason       'tool_calls'
    tool chosen          publish_pages
    arguments            {"course": "VVH2O", "section": 1, "pages": "all"}

**The model did not echo the list.** It answered in 35 tokens, finished
naturally, and the cap never fired. So the shape that could cost 975 tokens was
not the shape this model produced when actually asked - on three trials, on one
model, with one phrasing, which is what that is worth and no more.

It also produced something else worth writing down and NOT fixing here: it
passed `"pages": "all"`, which is not a page list. What the app does with that
is outside #166; it is recorded as a finding rather than repaired in passing.

**What this changes.** The caveat in `AssistModelClient.mostTokensPerReply`'s
doc comment and in `documentation/10-local-ai-assistant.md` -> Step 1 no longer
says "has not been measured". It says: sixty relative paths are 975 tokens, the
cut would land at about the thirty-first path, and the one generation measured
answered with a range instead. It does not change the cap. Raising a cap to
cover the worst imaginable call is the state #166 was about, and the advice in
`AssistWording.answerWasCutOff` is followable in exactly this case.

WHAT THIS FILE DOES NOT SHOW
----------------------------
  - **The fix itself.** The suite scores the tool NAME. It never runs the app,
    so nothing here says whether a call parsed out of a cut-off answer is
    refused. That is `AssistCutOffAnswerTests`' job.
  - **That the cap is the right SIZE.** It shows 512 changed no choice on these
    48 probes. The headroom argument for the number is in doc 10, and the
    measurement above is the one hole in it being filled, not the argument
    being re-run.
  - **Anything about Windows.** `plantoir-mcp.exe` and `LocalModel` were not
    measured; Windows has sent 512 all along, which is where the number came
    from.
  - **A probability.** Temperature 0 and ten trials; see "What this number is
    not" at the top.
  - **Anything about an idle machine.** Every clock here was taken on a Mac
    with other work on it, and the two uncapped arms of the same body, eight
    hours apart, differ by more than a factor of two on the runaway.
